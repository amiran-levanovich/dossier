# The CV path plans edits against the exemplar instead of rewriting it

When `master_cv.md` checks VERIFIED, `application-writer` no longer emits `cv.md`. It emits an **edit plan** — slot order, patched text, new slots, drops — against a **slot map** extracted from the exemplar, and `scripts/master_slots.py assemble` writes `cv.md` and `cv_trace.md` from it. The pattern is adapted from the `extract-latex-content` / `patch-latex-content` pair in [career-ops](https://github.com/santifer/career-ops).

The waste this removes is that every verbatim line was being **re-typed in full by the model and then diffed to discover it was verbatim**. `scripts/master_diff.py` exists precisely because the verbatim majority is the common case (`lifecycle/master_documents.md`: the exemplar turns the writer "from a generator into an editor"), so the pipeline was already paying to rediscover, per application, something the exemplar had already settled. The same inversion drops `master_cv.md` and `master_cv_trace.md` from the writer's inputs entirely — the slot map carries each slot's trace target inline, so verbatim slots inherit their trace lines during assembly and the writer authors trace lines only for what it patched or created.

## Considered options

**Slot ids are a hash of the slot's own text, not a position.** Positional ids (`b-0-2`) read better in a diff, but slot ids are stamped into `master_cv_trace.md`, which persists; one insertion into the exemplar renumbers everything below it and every stamped id goes stale in a file nobody thinks to re-stamp. Content-hash ids change only when the text changes — which is exactly when the trace line needs re-judging anyway. This is the invalidation doctrine `scripts/claim_ledger.py` already states: *automatic, never manual*.

**Blocks are atomic and bullets are scoped inside them**, rather than a flat list of content lines mirroring `master_diff.py`'s unit. A flat list makes it possible to assemble a bullet under the wrong employer's heading, and **no existing gate catches that**: a trace file maps claim → knowledge-base source, never claim → employer, so a misattributed bullet passes `trace_check.py`, passes the ledger, and reads as true. Scoping bullet ids inside their block makes the error unrepresentable instead of merely detectable — the same reasoning as ADR-0002.

**Trace inheritance joins on slot id, not on claim text.** Trace lines quote claims *abbreviated* (`core/tailoring_method.md`), so a trace line is not byte-equal to its bullet; a substring join would be unreliable in the common case and silently wrong when two bullets share wording — producing a `cv_trace.md` that passes `trace_check.py` while pointing a claim at the wrong source.

**Stamping — the one place a text join survives, deliberately.** Ids come *from* the exemplar, so the first stamp has nothing to join on but the claim text it is about to label. `stamp` therefore walks the trace and the slot list together **in document order** (`core/tailoring_method.md`: one trace line per claim-bearing element) and validates each pairing — the claim's content tokens must appear, in order, within the slot's text. Slots may be skipped, since structural lines carry no trace line, but a trace line matching nothing from the cursor onward exits 1 and writes nothing, and the full pairing table is printed for a human to read once. This is a judgment-shaped step in a repo whose scripts are meant to be judgment-free, which is why it is confined to a one-time, human-reviewed, loudly-failing operation instead of running per application: order-independent content matching was rejected because two similarly worded bullets make a short claim genuinely ambiguous, and an order-plus-content-fallback was rejected because silent recovery hides a misordered trace until it matters.

**Two ideas from the same exploration were rejected outright.** career-ops' payload-not-markup renderer (its issue #557) does not transfer: it strips HTML tag overhead from model output, and dossier's deliverable is markdown with rendering deferred to `standards/rendering.md`, so there is no markup layer to remove. Its zero-LLM JD skill-gap classifier is already here as `scripts/ats_coverage.py`, with a better middle bucket — keyed on knowledge-base verification state rather than mere prose presence.

## Consequences

**The gate is untouched.** `master_diff.py` runs unchanged after assembly, no longer as discovery but as a self-test proving the kept slots really are byte-verbatim rather than trusting the script that copied them. `application-verifier` receives the same reports it did before, plus the assembler's length line — which makes `standards/cv_rules.md`'s one-page rule judgable against a measured word count instead of the writer's estimate, where previously nothing measured it at all.

**`trace_check.parse_trace_file` must strip the `[id]` prefix before setting `tline.claim`.** Ledger keys are `sha256(claim, path, anchor)`; if the id leaks into the claim, every entry in every user's ledger silently stops matching and the next application pays full judgment on claims already judged CLEAN. This is the one genuinely dangerous line in the change and is pinned by test first. Stamping itself is safe: `claim_ledger.py record --document` hashes `master_cv.md`, while `stamp` writes only to `master_cv_trace.md`, so a VERIFIED exemplar stays VERIFIED.

**The writer no longer sees the document it is responsible for**, and content-hash ids are opaque, so a fumbled id is more likely than with positional ones. The assembler is therefore strict — any unknown id, duplicate, patch/drop contradiction, or new slot without a trace target exits 1 and writes **no file**, and the orchestrator re-dispatches the writer with the diagnostic. A partially assembled `cv.md` would pass `trace_check.py` while missing content, which is the failure this refuses to allow.

**The token saving is projected, not measured.** `scripts/session_metrics.py` on one real application before and after is the acceptance evidence; if the saving is marginal, the `trace_check.py` risk above is not worth paying and this should be reverted rather than kept for tidiness. Applications with no exemplar, or a CHANGED one, take the previous path unchanged.
